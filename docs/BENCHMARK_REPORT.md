# Benchmark report: advisory lock vs row locks only

The review of the proposal suggested serializing matching per security with an advisory
lock, benchmarking it against the row-locking design, and writing up the trade-off.
This is that write-up. The measured numbers are generated by the benchmark script into
`docs/BENCHMARK_RESULTS.md`. Always quote the numbers from that file, from your own machine.

## The two designs

| | `advisory` (default) | `row` |
|---|---|---|
| What serializes matching | `pg_advisory_xact_lock(security_id)`, taken at the start of the transaction | Only the `FOR UPDATE` locks on candidate orders and accounts |
| Orders on the same security | One at a time | Can overlap |
| Orders on different securities | Fully parallel | Fully parallel |
| Switch | `MATCHING_LOCK_MODE=advisory` | `MATCHING_LOCK_MODE=row` |

## How to reproduce

```powershell
npm run bench
```

It uses the **test** database only. For a bigger run:

```powershell
$env:BENCH_ORDERS=600; $env:BENCH_ROUNDS=5; npm run bench
```

## Method

- The same seeded random workload runs in both modes: prices 99 to 101, quantities 1 to 10, buy or sell at random.
- 16 orders are in flight at any moment, below the connection pool size of 20.
- Two scenarios: **one security** (everything contends for one book) and **five securities** (contention is spread).
- Each setting runs several rounds in a fresh process. The report shows medians. The two modes alternate who goes first.
- After each run the script checks correctness directly in the database: crossed-book pairs, executed + remaining = quantity for every order, and reserved cash and shares matching open orders.

## What to look at

1. **Correctness first.** For `advisory`, every correctness column must be 0. If it is not, that is a real bug to investigate. For `row`, a non-zero value, or unexpected errors such as a deadlock that survived its 3 retries, is a result worth reporting. It is what the advisory lock exists to prevent.
2. **Throughput and latency second.** Compare orders per second and p95 latency between the modes in each scenario.
3. **Scaling across securities.** In the five-security scenario, `advisory` should lose little, because different securities never wait for each other.

## The trade-off, in words

- **Advisory lock.** Matching on one security is serialized, which is how real matching engines work (one thread per symbol). It costs some parallelism on a single hot security. In return the candidate query always sees every earlier committed order, so the book cannot be left crossed, and fewer lock conflicts and deadlocks occur.
- **Row locks only.** Allows more overlap and can be faster when orders touch different resting orders. But candidate selection uses a snapshot taken before the locks are held, so two concurrent orders can each miss the other. Overlapping lock sets also make deadlocks possible, handled by retry.

The default is `advisory`: the engine's job is correctness first, and the benchmark
measures what that choice costs.

## Threats to validity

- Everything runs on one laptop, with the database and the Node process sharing the CPU.
- Orders call the service layer directly, so HTTP overhead is not measured.
- The workload is small and random. A real exchange has far more skewed traffic.
- Timing varies between runs, so compare the medians, not single numbers.
